Tier 2 — the same two containers, as a Pod on a real cluster

Tier 1 makes the argument with a plain-Java model of a Pod. This directory runs the real thing: a kind cluster, the same two service images as sidecar-pattern, and the same nginx template, mounted as a ConfigMap rather than copied. Nothing here is a fork of the Docker Compose version, so the comparison is exact.

Tier 2 is optional. Skipping it loses none of the pattern. ../docs/dependencies.md says what Kubernetes is, what it costs, and how to skip it. This page is the transcript, which is real output.

./demo.sh          # creates the cluster, runs six acts, deletes the cluster

One command starts everything and the same command stops it: demo.sh deletes the cluster when it finishes, or when it fails. To delete one by hand: kind delete cluster --name sidecar-demo.

Requires Docker (running), kind 0.33.0 (the script refuses any other), kubectl, a JDK 21, and a network the first time. kind pulls a node image of about a gigabyte. A cold run took about four and a half minutes; a run with the image already downloaded took about one.

What is running

ObjectWhat it is
gateway Deployment and ServiceThe payment provider from sidecar-pattern, unchanged. HTTPS only, TLS 1.3 only.
checkout DeploymentOne Pod, two containers. The service, and the proxy beside it as a native sidecar.
refunds DeploymentOne container, exactly as its team wrote it. Act 6 gives it a second, from outside.
sidecar-config ConfigMapsidecar-pattern's nginx template, the one file every proxy reads.
gateway-cert SecretThe provider's certificate, generated by demo.sh.

The two lists in k8s/checkout.yaml

containers holds the service. initContainers holds the proxy, with one extra line, restartPolicy: Always. That line makes it a native sidecar: it is started before the service, must be running before the service starts, and keeps running beside it. What is missing matters as much: there is no network_mode, no depends_on, and no network configured anywhere.

Deleting the cluster

What the run shows

  • Act 2 reaches a port that belongs to a different container, with no network settings in the manifest. That is a Pod.
  • Act 4 is the correction Tier 1 makes: killing the proxy restarted only the proxy. Its restart count went from 0 to 1, checkout's stayed 0, and checkout's start time did not change. A crash does not take a neighbour with it.
  • Act 5 is what is shared: delete the Pod and both containers go, and the replacement is a new Pod with a new address and new containers.
  • Act 6 adds a sidecar to a service whose manifest file has the same hash before and after.

What this still does not show

Tier 2 narrows the gap between the model and reality. It does not close it.

  • One node. There is no scheduler choosing between machines, and no node that fails.
  • A control plane that does not fail. It is one container on your laptop.
  • Injection by hand. Act 6 applies a patch. A real service mesh does it automatically for every Pod, through a mutating admission webhook, which this project names and does not build.
  • No restart back-off. The proxy was killed once. A container that keeps crashing is restarted with growing delays, which this run does not reach.
  • Version skew. The node image is Kubernetes v1.37.0. A kubectl more than one minor version away prints a warning and, in this run, still worked. Use one within a minor version of the node.
