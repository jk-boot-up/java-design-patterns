# Externalised Configuration Pattern — Video Narration Script

## 1. Externalised Configuration

Hello, and welcome. This video explains the Externalised Configuration pattern, in Java. This video is presented by Jayasekhar Konduru. First, a simple definition. Externalised configuration keeps the values your program needs outside the program itself. And the program reads them while it runs. So changing one of those values does not mean building and releasing a new program. Think of a greengrocer with a chalk board outside the shop. The prices are not painted on the wall. To change a price, someone rubs it out and chalks a new one, in thirty seconds. But because the board is outside, anyone can also write nonsense on it. In our online store, delivery is free for anyone spending over fifty pounds. And the marketing team want that to be thirty-five pounds by Saturday morning. By the end, you will know why a well-written constant can still be in the wrong place. Exactly where the value must be read. And the four safety checks a value loses when it leaves your code, and how to get them back.

## 2. The Scenario

Here is the scenario. The shop's delivery page makes one promise. Spend over fifty pounds, and delivery is free. Spend less, and delivery costs four pounds ninety-nine. Three baskets are waiting at the checkout. Every demo uses these same three. The first holds sixty-two pounds of goods. The second, forty-eight pounds. The third, thirty-one pounds fifty. With a fifty-pound threshold, the first ships free, and the other two pay. Then, on Friday afternoon at half past four, marketing ask for a change. For the weekend campaign, free delivery over thirty-five pounds, instead of fifty. A one-number change. Remember that Friday half past four.

## 3. Where the Number Lives Today

Here is where the fifty pounds lives today. It is a constant in the checkout class, with a clear name. And there is nothing wrong with it. It has a name, so it is not a mystery number. It is typed as money, so it cannot be mistaken for anything else. It appears in one place only. Any code reviewer would approve it. So let's be clear. This pattern does not fix bad code. It fixes a value that sits somewhere that changes too slowly. The code is fine. The problem is what it takes to turn fifty into thirty-five.

## 4. What Changing One Number Costs

First demo: what changing one number costs. The change goes through a normal release process. Editing the constant takes fifteen minutes, and is done at a quarter to five on Friday. Then code review, forty-five minutes. But it finishes on Monday morning. Because the release window closed at five on Friday, and only reopens on Monday. Then building and testing: twenty-five minutes. Release approval: half an hour. Then the release itself, and twenty minutes watching it. Two hours and fifteen minutes of real work. And it goes live on Monday at a quarter to eleven. Two days after the Saturday promotion started. All weekend, the campaign promises free delivery over thirty-five pounds, and the shop charges as if it were fifty. Now try to remove a step. Code review stops typos reaching customers. Tests stop broken code being released. Approval proves releases are controlled. And weekday windows exist because the people who would spot a bad release are at work on weekdays. Nothing on that list is waste. And the promotion still misses its weekend. That is not a code quality problem.

## 5. The Pattern

So here is the idea, and it starts with a distinction. Some values in your program are decisions about behaviour. The order of steps, how a total is built, the method you chose. Those belong behind the release process. And you should be glad they are hard to change. Other values are business policy. A threshold, a page size, a promotion window, how long a session lasts. These change on someone else's timetable, usually not an engineer's. Here is the key sentence. Putting a policy value behind the release process does not make it safer. It makes it late. So externalised configuration keeps that kind of value outside the program. And reads it while the program runs. That is the whole pattern.

## 6. Three Moves

It takes three moves. Most explanations only give you two. Move one. The value comes from outside. And it is read every single time it is used. Not once, when the program starts. Every time. Move two. The code still carries its own default value. Because the outside source might be unreachable. And a shop that stops selling because a settings server is down is worse than one with the number built in. Move three, the one usually skipped. While the value lived in the code, four things protected it. The compiler, which refuses to build if you type the word fifty where a number belongs. The type system, which keeps it as money. A code reviewer, who would question minus one pound. And version control, which records who changed it, when, and what it was before. None of those four follows the value out of the code. If you want them, you must rebuild them yourself.

## 7. Who Does What

Let's name the pieces. There are five. First, the checkout. It works out whether a basket gets free delivery. That arithmetic is the same in both versions of this project. Second, the settings reader. It is the only part that knows about the outside world. Checkout asks it for the threshold, and gets back an amount. Checkout cannot tell whether it came from a server, a file, or the built-in default. Third, the declared setting. A small record holding four things. The setting's name, its default, the lowest sensible value, and the highest. This will replace the compiler. Fourth, the configuration source. It just stores text under names. It has no idea whether the text makes sense. Fifth, a change log. It records every change: the setting, the new value, the old value, who, and when. That replaces version control. The project has two checkouts, one with the number in the code, and one that reads it. And two settings readers, one that trusts any text, and one that checks it. The same bad values go through both.

## 8. The One Line That Is the Pattern

Here is the configured checkout, and very little of it is new. It receives a basket. It asks the settings reader for the free-delivery threshold. If the basket is worth at least that much, delivery is free. Otherwise, it charges the standard fee. Only one line differs from the hard-coded version. Instead of using a constant, it asks for a setting. Now the most important detail in this video. Not what that line says, but where it sits. It sits inside the method that prices each basket. So every time a customer reaches delivery, the threshold is fetched again. Tidy-minded developers want to move it to the start, and keep the value. It looks neater. And it breaks the pattern. Because now the only way to pick up a new value is to restart the program. One test exists only to fail if someone makes that tidy-up. And one more thing. What comes back is the amount, plus a note of where it came from. Once a value can change, the question becomes: which threshold applied to this order, and where did it come from?

## 9. Four Seconds

Second demo: what it buys. It starts with nothing configured. So every quote uses the built-in default, and the shop behaves exactly as before. The sixty-two-pound basket ships free, and the other two pay. Adopting the pattern changed nothing on its own. Then someone in marketing types thirty-five into a box. Four seconds later, the very next basket is priced against thirty-five pounds. And the forty-eight-pound basket now ships free. No rebuild. No release. No restart. Nobody approved anything. Four seconds, against two hours of work spread over a whole weekend. That is the business case for this pattern. That is the good news. The rest of this video is the bill.

## 10. The Bill, Part One — When the Source Goes Away

Third demo: the source goes away. The connection to the settings server drops. Every setting falls back to its built-in default. And the shop keeps selling. That is exactly why move two insisted on a default. But listen to what it quietly lost. The threshold is back to fifty pounds. The promotion is off. The campaign is still promising thirty-five pounds, and the shop is charging as if it were fifty. And nothing reports it. No error, no log, no alert. The only trace is that little note saying where the value came from. Surviving an outage quietly is not the same as surviving it correctly.

## 11. The Bill, Part Two — A Number Nobody Checked

Fourth demo: a number nobody checked. Saturday morning, twelve minutes past nine. Someone types minus one into the box. Perhaps they hit the wrong key. The settings server stores it, because storing text is all it does. Now every basket is worth more than minus one pound. So every basket ships free. Including the thirty-one-pound basket, where delivery costs more than the shop earns. And nothing goes wrong, as far as the software can tell. No error, no crash, no alert. Minus one is a perfectly valid number. The program was told the threshold is minus one pound, and it obeys. The first sign is the profit report, on Monday. That value reached the live shop in four seconds. With no compiler, no review, and no tests in the way. That is what you traded the release process for.

## 12. The Bill, Part Three — Not a Number at All

Fifth demo: not a number at all. Eight minutes later, someone tries to fix it. And types the word fifty, in letters. That cannot be turned into money. So an error is thrown, and nothing catches it. Not one basket can be priced. Every customer at the delivery step gets an error page. The shop is down. Taken down by someone typing a word into a box, with no code changed at all. The compiler would have refused this. But the compiler is no longer between a person's fingers and your live shop. And here is an uncomfortable comparison. Of these two failures, this one is better. Because you find out. Errors spike, someone is called, and it is fixed within minutes. Minus one runs all weekend, quietly, and the first to notice is an accountant. A loud failure is a bad afternoon. A quiet failure is a bad quarter.

## 13. The Four Guards, and What Replaces Them

So let's rebuild the four protections, one by one. None of them is difficult. The compiler refused the word fifty. Its replacement is a typed setting. It tries to turn the text into money, and rejects it at the door if it cannot. A reviewer would have questioned minus one pound. Its replacement is a declared range: a lowest and a highest allowed value. Version control knew who changed what, and when. Its replacement is an audit trail, recording that on every change. And a bad release was undone by a new release. Its replacement is a rollback that is as fast as the change was. Notice what this list is not. Not a framework, and not clever. Four small, ordinary pieces of code. This pattern goes wrong in real systems because the first two moves work on their own. So nobody gets round to the third.

## 14. Declared, and Validated at the Boundary

Sixth demo: declared, and checked at the door. The setting is now declared, out loud. It holds money. It must be between five pounds and two hundred pounds. And it defaults to fifty pounds. Why those limits? Below five pounds, you are giving free delivery on a packet of crisps. Above two hundred, almost nobody qualifies, and the promotion is broken the other way. Those are business judgements. And that is why the program must enforce them. Now the word fifty is still in the settings. It is refused at the door. The shop falls back to fifty pounds, and keeps trading. Then a good value, thirty-five, arrives, and passes. And the reader remembers it as the last known good value. Then someone types minus one again. It is refused. And the shop falls back, not to fifty, but to thirty-five, the last good value. That matters. Someone deliberately set thirty-five an hour ago. Reverting to fifty because of an unrelated typo would cancel a promotion nobody decided to cancel. And both refusals are recorded, loudly. A guard that silently swallows bad input is only half a guard.

## 15. The Trail, and a Rollback in Four Seconds

Seventh demo: the trail, and a rollback. Here is every change made to that one setting. Five changes, in less than a day. Each records the new value, the old value, who made it, and exactly when. Five changes to a business-critical number in one day. And none of them is in version control. This list is its replacement. The question you will really be asked is not: what is the threshold now? You can just look. It is: what was it at nine o'clock on Saturday morning? Without this list, there is no honest answer. Then the fourth protection. Saturday, twenty to twelve. Someone on call sees the threshold is minus one, and rolls it back. Four seconds later, the shop is using thirty-five pounds again. Nobody had to remember the old value. The log had it. The same fix through the release process would have gone live on Monday. A bad release takes a release to undo. A bad value takes four seconds. So externalised configuration is not a way to avoid control. It is a way to control a change in seconds, instead of days.

## 16. What to Externalise, and What Never To

So, what should you move outside the code? Ask two questions, in this order. First: does this value change on an engineer's timetable, or someone else's? A free-delivery threshold, a page size, a timeout, or a promotion window? Someone else's. Those are candidates. The order of steps, how a total is built, the method itself? Those belong in the code, behind the release process. Second: what could I break by typing into that box? If the answer is the whole shop, the protections are not optional. They are the price of entry. One last distinction. This is not the same as a feature flag. A setting like a threshold lives as long as the product. A feature flag switches between two versions of code. And a flag is meant to be deleted, once the new version is proven.

Take a number out of the code, and you also take out the compiler, the reviewer, and the history, so rebuild them on the outside.
