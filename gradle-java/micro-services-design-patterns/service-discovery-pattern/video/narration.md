# Service Discovery Pattern — Video Narration Script

## 1. Service Discovery

Hello, and welcome. This video explains the Service Discovery pattern in Java, and it is written and presented by Jayasekhar Konduru. Let's start with the simple definition. Service discovery means that instead of writing a service's address into the code that calls it, you keep a shared list of who is running right now, and the caller asks that list every time it needs an address. Programs put themselves on the list when they start, and they drop off it when they stop. That's the idea in a sentence. The rest of the video does it properly, by building a real working Java project: an online shop whose pricing service runs as several copies of itself, and a checkout that has to reach one of them. By the end you'll know why a written-down address turns an ordinary deployment into an outage, what a lease is and why a registration has to expire, and — the part that usually gets skipped — why the list is guaranteed to be wrong for a few seconds at a time, and what a caller has to do about that.

## 2. The Scenario

Here is the situation. The shop's pricing service is busy enough that one copy of it is not sensible any more, so it runs as three. They are the same program, started three times, on three machines. The important thing about those three is that they are interchangeable. Any of them can answer any question, and they all give the same answer, because the price of an espresso machine does not depend on which machine you happen to ask. Now the checkout needs a price. To ask for one it needs an address. And that raises a question which has no interesting answer in a single program, and no easy one here: which of the three does it call, and how does it find out?

## 3. The Obvious Answer — Write It Down

The obvious answer is to write the address down, and I want to be fair to it, because this is what every system starts with and starting there is right. The class in the project is called hardcoded pricing client. It holds one string, pricing dash one, and it calls it. That is the whole class. There is no bug in it. It is four lines and every one of them is correct. It is fast, it has no dependencies, it cannot be misconfigured, and every test you would think to write against it passes. When the shop had one pricing instance, this was exactly the right amount of code. So keep that in mind as we break it. What goes wrong here is not a mistake somebody made. It is the world changing underneath a decision that was correct when it was taken.

## 4. Then Somebody Deploys Pricing

Then somebody deploys pricing. A rolling deployment stops the first instance so it can be replaced with a new version. That is not a fault. That is Tuesday afternoon. And the checkout is now down. Not slow. Down. It asks for a price and gets nothing back, and it will go on getting nothing back until somebody changes it. Now here is the part that stings. At that exact moment, pricing two and pricing three are up, healthy, and doing nothing, three metres away in the same rack. The client cannot use either of them. And no amount of care inside that client would help, because a constant is not a question you can ask again later. It was told about one machine, once, and it has no way of ever finding out about another.

## 5. Why That Really Hurts

It is worth naming the damage properly, because it is wider than one outage. A routine deployment takes the caller down. Scaling up buys you nothing at all — start a fourth instance for a busy Friday and no existing caller will ever send it a single request, so you are paying for capacity that cannot be reached. And a crash has no fallback, because there is nothing to fall back to. But none of those is the diagnosis. The diagnosis is this. The set of running instances changes several times a day — every deployment, every autoscaling event, every crash. The source code of the callers changes about once a fortnight. A fast-moving fact has been stored inside a slow-moving artefact. And that is why the usual first suggestion does not work. Move the address into a configuration file and you have moved the fact one step, and improved the ratio slightly. A human still has to edit that file, and restart the process, and — worst of all — that human still has to notice.

## 6. The Service Discovery Pattern

The pattern is usually stated something like this. Instances register themselves with a registry when they start, renew that registration from time to time, and deregister when they stop; and callers query the registry for the current instances of a service. In plain words: don't write the address down. Ask, every time. And then there is a second half, which is not in most statements of the pattern and which this video is going to spend real time on: be ready to be told wrong. Notice what the first half fixes. An instance is reachable the moment it starts, with no configuration change anywhere. A polite shutdown is invisible to callers. Scaling up works. Nobody edits anything. And notice what it cannot fix, which is that a program which has crashed cannot send a message saying it has crashed. For a few seconds after a crash, the list will confidently hand out the address of something that is not there. That is not a flaw in any particular registry. It is the shape of the problem.

## 7. An Analogy

The analogy to hold on to is a taxi rank. One way to get a taxi is to keep the mobile number of a driver called Dave. That works beautifully, and it keeps working, right up until the evening Dave is off. And then it goes on not working, while eleven other drivers in town would happily take you, because your phone knows about Dave and nobody else. The other way is a taxi rank. You know no driver's name at all. You go to the rank and take whoever is at the front. Drivers join the rank when they start a shift and leave it when they finish, and none of that requires you to learn anything or change anything. The rank is the registry. The drivers are the instances. And now here is the detail that makes this more than a nice picture, so listen for it. What do you do if you get into a car whose driver has just been called away? You do not stand there insisting. You take the next one. Hold on to that, because in the code it turns out to be four lines, and without them the whole pattern falls over exactly when you need it.

## 8. The Roles

So, the pieces. At the top there is the caller: the class in the project is called discovering pricing client. It holds a reference to the registry rather than to an instance, and that one difference is the entire pattern. It holds a source of addresses where the old version held an address. In the middle sits the registry itself, called service registry. It keeps one entry per instance, and each entry is a lease with a timestamp on it. To the side of it is that lease — a tiny record holding the instance and the time of its last heartbeat. It is the only thing in the project that stores a time, and it is what turns an ordinary map into something that forgets. On the right are the pricing instances, and the direction of the arrows there is worth saying out loud, because it is easy to get backwards. The arrows run from the instances into the registry. Instances announce themselves. Nothing in this system ever calls out to a service to ask whether it is alive. The reason is neat: a registry that polled everybody would need a list of who everybody is, and building that list is the original problem again, one level up. And kept deliberately beside the pattern rather than inside it is the hardcoded client, so that the comparison is something you can run rather than something I assert.

## 9. The Registry — and the One Line That Matters

Now the registry, and most of it is deliberately boring. Registering is putting an entry in a map. Deregistering is removing one. A heartbeat is putting the same entry back with a fresher timestamp. If the class stopped there it would be a phone book. What makes it a registry is one comparison, and it lives in the method that answers the question who is running. The comparison is: take the current time, subtract the time of this entry's last heartbeat, and if the difference is bigger than the lease, throw the entry away. In this project the lease is three thousand milliseconds. Ask yourself why a registration needs to expire at all. Instances deregister when they shut down, so why not trust them? Because a program that has crashed cannot send a message saying it has crashed. The registry cannot detect death. It can only notice silence — and silence is the one thing a dead process is extremely reliable at producing. Two small details worth hearing. The expiry happens when somebody asks, not on a timer, so there is no background thread anywhere in this project. And a heartbeat from an instance the registry has never heard of does nothing at all, quietly, because otherwise a stray heartbeat could walk a deregistered instance back onto the list.

## 10. The Caller — Ask, Then Try The Next One

And here is the caller. There are two separate behaviours in this short method and it is worth pulling them apart. The first is discovery. Ask the registry who is running, then call one of them. Notice when the asking happens: at the top of every single call, not once when the program starts. That matters more than it looks. A client that looks the list up once and keeps it for the life of the process has reinvented the hardcoded address with extra steps. The second behaviour is the loop. If the instance it was given does not answer, it notes the word stale, and it moves down the list to the next name. That is the taxi driver who has been called away. It is a loop and a caught exception, and it is the difference between discovery that works and discovery that only works on good days. And look at the last line, because it is also a decision. When every instance it was offered is dead, the client fails. It does not hang, and it does not invent a price. Everything is down is a real answer, and the client is allowed to give it.

## 11. A Deployment, and a Scale-Up, With a Registry

Now the same deployment, with a registry in place. Follow the number of instances offered, because that number is the whole story. The first lookup is offered three instances, and the price comes back in ten milliseconds. Then the deployment happens. Pricing one shuts down politely this time, so on the way out it takes itself off the list. The next lookup is offered two, and pricing two answers. Then a fourth instance starts up for a busy Friday and registers itself. The lookup after that is offered three again. Three, then two, then three. A deployment and a scale-up, and the price came back correctly every single time. And here is the line that is the actual return on the pattern: no code changed, no restart, no configuration edit. Nobody was paged. Nobody noticed. The mechanical cost of all that is one extra message per call, the one that asks the registry who is running.

## 12. The Half That Gets Skipped: A Crash

And now the half that usually gets skipped. This time pricing one does not shut down politely. The process simply dies. No deregistration, because there is nobody left to send it. So the client asks the registry who is running, and it is offered two instances. Listen to that again. It is offered two instances, and the first one is dead. The registry is not wrong because somebody wrote it badly. It is wrong because it cannot be right. The client calls that first instance, gets nothing, writes the word stale into its log, and moves down the list. Pricing two answers, and the shopper gets a price. Count the cost of the crash: five milliseconds, and a line in a log. Without that loop it would have cost an outage — the same outage we saw at the start, from the pattern that was supposed to have fixed it. Which is why I said this is a pair rather than one idea. A registry without a caller that copes with stale entries fails every time an instance dies, and dying instances are precisely the situation it was introduced for.

## 13. The Lease Expires, and the List Corrects Itself

So how long is the registry wrong for? This is the act with no caller in it at all. Time simply passes, one second at a time, and we ask the registry how many instances it lists. Immediately after the crash: two. One second later: still two. Two seconds: two. Three seconds: two. Four seconds later: one. For three full seconds the registry confidently names a dead process, because the living instance keeps renewing its lease and the dead one cannot. On the fourth second the dead lease expires unrenewed, the entry is dropped, and the list becomes true again. That window is the honest price of this pattern, and I want to be straight about it, because every real registry has one. Eureka has it. Consul has it. The endpoints controller in Kubernetes has it. You can make the window shorter by sending heartbeats more often, and then every instance spends more of its life telling a registry that it is alive. That is a real trade and you can pick either side of it. What you cannot do is make it zero, because the only message that would close the window is the one a crashed process cannot send. So the right response is not to tune the lease until the problem goes away. It is to write callers that expect to be handed a bad address now and then.

## 14. What the Tests Pin Down

The tests are worth a minute, because of what they choose to assert. Both clients return four hundred and forty nine pounds ninety nine. So a test that checked the price would pass on the hardcoded version too, and would prove nothing at all. Instead the tests pin the behaviours that only discovery gives you. That a new instance is found with no code or configuration change. That a polite shutdown takes effect immediately. That a crashed instance stays on the list, because it could not say otherwise — yes, there is a test asserting that the registry is wrong, on purpose. That a stale entry is handed out and the caller copes by trying the next one. That a lease is still good on its very last millisecond, which is the kind of boundary that quietly drifts. And that the registry is consulted on every call rather than once. There is also a test pinning the naive client's failure, so the comparison cannot rot silently as the project changes. Nineteen tests, and not one of them calls sleep, even the ones about a three second lease — because the clock is simulated and four seconds of waiting is a number added to a counter.

## 15. The Costs, Honestly

Now the costs, because a pattern presented without them is a sales pitch. First, the registry is a new thing that has to be up. If it goes down and nobody can look anything up, then nothing can call anything, which is a worse failure than the one we started with. That is why real registries are run as a cluster of several nodes, and why real clients usually keep the last good list they were given as a fallback. Which leads to the second cost, and it is an uncomfortable one. That fallback deliberately reintroduces staleness. Caching the list for a second or two is normal and sensible, and it means you are knowingly choosing to sometimes be wrong, because the alternative is being unavailable. The loop in the caller is what makes that choice affordable. Third: nothing is where you left it. Which instance served a request is no longer something you can read out of a configuration file — it is a decision taken at runtime. That is the whole point, and it means your logs have to record which instance answered, or debugging becomes guesswork. And finally, the honest one. If a service has exactly one instance, started by hand, that never moves, then a constant is the right answer and a registry is theatre. The pattern earns its keep the moment the number of instances stops being one — or, in practice, the first time anybody wants to deploy without downtime.

## 16. Thanks for Watching

That's the service discovery pattern. The full source, the written notes, the diagrams and an animated walkthrough are all in the repository, and everything runs offline with nothing installed but a Java development kit — no Docker, no Consul, no Kubernetes. If you try one exercise, try this one. Delete the loop from the caller, so that it uses only the first instance the registry offers, and then run the tests. Watch which ones fail. Every deployment test still passes. Only the crash tests break. That is exactly the trap a real system falls into, because deployments happen constantly while you are testing, and crashes do not. You can ship a registry that looks perfect for months and fails the first night something dies badly. It takes two minutes, and it is the moment that trying the next name stops being advice and becomes code.
