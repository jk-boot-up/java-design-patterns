Service Discovery Pattern — Video Narration Script

1. Service Discovery

Hello, and welcome. This video explains the Service Discovery pattern, in Java. This video is presented by Jayasekhar Konduru. First, a simple definition. Instead of writing a service's address into the code that calls it, you keep a shared list of who is running right now. The caller asks that list every time it needs an address. Programs add themselves to the list when they start, and drop off it when they stop. Think of a taxi rank. You do not need to know any driver's name. You just take whoever is at the front. In our online store, the pricing service runs as several copies. And checkout has to reach one of them. By the end, you will know why a written-down address turns an ordinary release into an outage. What a lease is, and why a registration must expire. And why the list is always wrong for a few seconds at a time, and what a caller must do about it.

2. The Scenario

Here is the scenario. The shop's pricing service is busy. So it runs as three copies of the same program, on three machines. The three copies are interchangeable. Any of them can answer any question. And they all give the same answer. The price of an espresso machine does not depend on which machine you ask. Now checkout needs a price. To ask for one, it needs an address. So which of the three does it call? And how does it find out?

3. The Obvious Answer — Write It Down

The obvious answer is to write the address down. Every system starts this way, and starting there is right. The class in the project is called the hard-coded pricing client. It holds one name, pricing one, and calls it. That is the whole class. There is no bug in it. It is fast, simple, and cannot be misconfigured. Every test you would write against it passes. When the shop had one pricing copy, this was exactly right. So keep that in mind as we break it. What goes wrong is not a mistake. It is the world changing under a decision that was correct when it was made.

4. Then Somebody Deploys Pricing

First demo: somebody releases a new version of pricing. A rolling release stops the first copy, so it can be replaced. That is not a fault. It is an ordinary afternoon. And checkout is now down. Not slow. Down. It asks for a price, and gets nothing back. And it will keep getting nothing, until somebody changes the code. Here is the painful part. At that exact moment, pricing two and pricing three are up, healthy, and idle. The client cannot use either of them. It was told about one machine, once. And it has no way of ever learning about another.

5. Why That Really Hurts

The damage is wider than one outage. A routine release takes the caller down. Adding capacity does nothing: start a fourth copy for a busy Friday, and no caller will ever use it. And a crash has no fallback, because there is nothing to fall back to. But none of those is the real diagnosis. Here it is. The set of running copies changes several times a day. With every release, every scale-up, and every crash. But the callers' code only changes every couple of weeks. A fast-changing fact has been stored in a slow-changing place. That is why moving the address into a settings file does not really help. A person still has to edit the file, restart the program, and most of all, notice.

6. The Service Discovery Pattern

Here is the pattern, as it is usually stated. Each copy registers itself with a registry when it starts. It renews that registration regularly. And it removes itself when it stops. Callers ask the registry for the current copies of a service. In plain words: do not write the address down. Ask, every time. And there is a second half, which most descriptions leave out. Be ready to be told something wrong. The first half fixes a lot. A new copy is reachable the moment it starts. A polite shutdown is invisible to callers. Adding capacity works. Nobody edits anything. But it cannot fix one thing. A program that has crashed cannot send a message saying it has crashed. So for a few seconds after a crash, the list will hand out the address of something that is gone. That is not a flaw in any registry. It is the nature of the problem.

7. An Analogy

Here is the analogy: a taxi rank. One way to get a taxi is to keep the phone number of a driver called Dave. That works well, until the evening Dave is off. Then it keeps not working, while eleven other drivers in town would happily take you. Because your phone only knows about Dave. The other way is a taxi rank. You know no driver's name. You just take whoever is at the front. Drivers join the rank when their shift starts, and leave when it ends. And you never need to learn anything. The rank is the registry. The drivers are the copies of the service. And here is the detail that matters. What if you get into a car whose driver has just been called away? You do not stand there insisting. You take the next one. Remember that. In the code, it is a tiny loop, and without it the whole pattern fails exactly when you need it.

8. The Roles

Let's name the pieces. First, the caller, called the discovering pricing client. It holds the registry, not an address. That one difference is the whole pattern. Second, the registry. It keeps one entry per running copy. Each entry is a lease, with a timestamp. Third, that lease. A tiny record of the copy, and the time of its last heartbeat. A heartbeat is a regular message saying: I am still alive. The lease is what lets the registry forget. Fourth, the pricing copies themselves. Notice the direction. The copies announce themselves to the registry. Nothing ever calls out to a service to ask if it is alive. Because to do that, the registry would need a list of everyone, which is the original problem again. And kept beside the pattern, for comparison, is the hard-coded client.

9. The Registry — and the One Line That Matters

Now the registry, and most of it is deliberately boring. Registering adds an entry to a list. Removing takes one out. A heartbeat puts the same entry back, with a fresher time. If it stopped there, it would just be a phone book. What makes it a registry is one check. When someone asks who is running, it looks at each entry. How long since its last heartbeat? If it is longer than the lease, the entry is thrown away. In this project, the lease is three seconds. Why must a registration expire at all? Copies remove themselves when they shut down, so why not trust them? Because a crashed program cannot say it has crashed. The registry cannot detect death. It can only notice silence. And a dead program is very reliable at being silent. One more detail. The expiry check happens when someone asks, not on a timer. So there is no background thread anywhere in this project.

10. The Caller — Ask, Then Try The Next One

Here is the caller. It has two separate behaviours. The first is discovery. Ask the registry who is running, then call one of them. And notice when it asks: on every single call, not once at startup. That matters. A client that looks up the list once, and keeps it forever, has just rebuilt the hard-coded address with extra steps. The second behaviour is the loop. If the copy it was given does not answer, it logs the word stale. And it moves on to the next name on the list. That is the taxi driver who has been called away. It is a loop and a caught error. And it is the difference between discovery that works, and discovery that only works on good days. And at the end, if every copy it was offered is dead, the client fails. It does not hang, and it does not invent a price. Everything is down is a real answer.

11. A Deployment, and a Scale-Up, With a Registry

Second demo: the same release, with a registry. Listen to how many copies are offered each time. That number tells the whole story. The first lookup is offered three copies. The price comes back in ten milliseconds. Then the release happens. Pricing one shuts down politely, and removes itself from the list on the way out. The next lookup is offered two, and pricing two answers. Then a fourth copy starts for a busy Friday, and registers itself. The next lookup is offered three again. Three, then two, then three. A release and a scale-up, and the price came back correctly every time. No code changed. No restart. No settings edited. Nobody was called out. Nobody noticed.

12. The Half That Gets Skipped: A Crash

Third demo, and this is the half that usually gets skipped. This time, pricing one does not shut down politely. The program simply crashes. It does not remove itself, because there is nobody left to do it. The client asks the registry who is running. It is offered two copies. And the first one is dead. The registry is not wrong because it was badly written. It is wrong because it cannot be right. The client calls the first copy, and gets nothing. It logs the word stale, and moves on. Pricing two answers, and the shopper gets a price. The crash cost five milliseconds, and one line in a log. Without that loop, it would have cost an outage. So a registry and a caller that copes with wrong entries are a pair. Without the loop, the registry fails every time a copy dies. Which is exactly the situation it was meant for.

13. The Lease Expires, and the List Corrects Itself

Fourth demo: how long is the registry wrong for? There is no caller in this demo. Time just passes, one second at a time, and we ask how many copies the registry lists. Right after the crash: two. One second later: still two. Two seconds: two. Three seconds: two. Four seconds later: one. For three whole seconds, the registry names a dead program. The living copy keeps renewing its lease, and the dead one cannot. On the fourth second, the dead lease expires, and the list becomes true again. That gap is the honest price of this pattern. Every real registry has one: Eureka, Consul, and Kubernetes too. You can shorten the gap by sending heartbeats more often. But then every copy spends more time saying it is alive. You cannot make it zero. Because the one message that would close the gap is the one a crashed program cannot send. So do not try to tune the problem away. Write callers that expect a bad address now and then.

14. What the Tests Pin Down

The tests are worth a moment, because of what they choose to check. Both clients return the same price. So a test that only checked the price would pass on the hard-coded version too. And prove nothing. Instead, the tests check what only discovery gives you. A new copy is found, with no code or settings change. A polite shutdown takes effect at once. A crashed copy stays on the list, because it could not say otherwise. Yes, one test deliberately checks that the registry is wrong. A wrong entry is handed out, and the caller copes by trying the next one. A lease is still valid on its very last millisecond. And the registry is asked on every call, not just once. Nineteen tests, and not one of them waits. Even the ones about a three-second lease. Because the clock is simulated.

15. The Costs, Honestly

Now the costs, because a pattern without its costs is a sales pitch. First, the registry is a new thing that must stay up. If nobody can look anything up, nothing can call anything. That is worse than where we started. So real registries run as several servers. And real clients keep the last good list, as a fallback. Second, that fallback deliberately brings back out-of-date answers. Keeping the list for a second or two is normal and sensible. You are choosing to be sometimes wrong, rather than unavailable. The caller's loop is what makes that choice safe. Third, nothing is where you left it. Which copy served a request is decided while the program runs. So your logs must record which copy answered, or debugging becomes guesswork. And finally, the honest one. If a service has exactly one copy, started by hand, that never moves, a written-down address is the right answer. The pattern earns its keep the moment there is more than one copy. Or the first time anyone wants to release without downtime.

16. Thanks for Watching

That's the Service Discovery pattern. If you remember one sentence, make it this one. Do not write the address down, ask every time, and be ready to be told wrong, by trying the next name on the list. The full source code, written notes, diagrams, and an animated walkthrough are all in the repository. It runs offline, with nothing installed except a Java development kit. Here is one exercise to try. Delete the loop from the caller, so it only uses the first copy it is offered. Then run the tests. Every release test still passes. Only the crash tests fail. That is the real trap. Releases happen all the time while you test, but crashes do not. So a registry can look perfect for months, and fail the first night something crashes.
