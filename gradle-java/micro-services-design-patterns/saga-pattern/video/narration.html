Saga Pattern — Video Narration Script

1. Saga

Hello, and welcome. This video explains the Saga pattern, in Java. This video is presented by Jayasekhar Konduru. First, a simple definition. Sometimes one job has to happen in several different places. And you cannot keep them all on hold until you are sure of all of them. So you let each piece finish on its own. And for each piece, you write down the action that cancels it. If a later piece fails, you walk backwards, cancelling the ones that already finished. Think of booking a holiday: a flight, a hotel, and a hire car. If the car falls through, you cancel the hotel, then the flight. In our online store, one checkout has five steps, in five different services. Reserve the stock. Take the payment. Create the order. Book the parcel. Send the email. And then the courier refuses the address. The mechanism is small. This video is really about the three things undoing costs you, which almost nobody mentions.

2. One Checkout, Five Services

Here is the shop. Somebody buys a kettle for seventy pounds ninety-five. For that, five things must happen. Reserve the kettle, so nobody else takes it. Take the money. Create the order record. Book a courier to deliver it. And email the customer to say it is on the way. Here is what makes it hard. Those five things live in five different services. Each has its own database. And the money actually leaves through a card network that belongs to nobody in this building. So there is no single database underneath all of it. And without a single database, there is nothing single to roll back. Remember that sentence. Everything else in this video follows from it.

3. What Everybody Writes First

Here is what everybody writes first. And it is not stupid code. Four calls, one after another, inside one try block. Reserve the stock. Charge the card. Create the order. Book the courier. If anything goes wrong, catch the problem, write a line to the log, and return nothing. It sounds responsible. There is error handling. Nothing crashes. In a code review, this passes. Now let's hear what it does when the fourth call fails.

4. The Courier Refuses

No courier covers the delivery address. So the fourth call fails. The catch runs, writes its line, and the method returns nothing. Now count what is left behind. The card has been charged seventy pounds ninety-five. A kettle is still reserved, so nobody else can buy it. The order record says confirmed. And there is no parcel, and there never will be. In one sentence: the customer has paid for something that will never arrive. And here is the worrying part. Nothing looked wrong. No error escaped, no alert fired. There is one line in a log file, read weeks later, by someone investigating a complaint. The project has four tests for exactly this. The money stays taken. The stock stays reserved. The order stays confirmed. The failure is silent. All four tests pass. They are passing tests that prove the shop is broken.

5. No, @Transactional Does Not Fix It

At this point, someone always says: just add the Transactional annotation. Let's take that seriously. It is the biggest misunderstanding in this subject. That annotation wraps your method in a transaction, on the one database this service owns. That is all it does. It cannot reach the stock service's database. It cannot reach payments. And it certainly cannot reach the card network, where the money went. So when shipping fails and your transaction rolls back, only this service's own writes are undone. The seventy pounds ninety-five is still gone. There is a technology that can span all five, called two-phase commit. It works. But almost nobody uses it for this. It makes every service hold a lock while it waits for the others. So the stock table stays locked while you wait for a courier's website to answer. One slow courier, and under load, the shop stops. So there is no rollback. If we want the shop put back, we must put it back ourselves.

6. You Already Know How This Works

Here is the same problem, away from any computer. You are booking a holiday by phone: a flight, a hotel, and a hire car. You cannot keep all three on hold until you are happy with all three. The airline will not hold a seat while you ring the hotel. So you book them one at a time. And each booking is final the moment you make it. Then the car hire company says they have nothing that week. There is no magic button that undoes the last hour. What you have is each booking's cancellation policy. So you ring the hotel, and cancel the room. Then you ring the airline, and cancel the flight. And you end up back where you started. Approximately. Hold on to that word, approximately. Most of this video lives inside it.

7. A Step That Carries Its Own Undo

Here is the mechanism, and it is small. Every step in the checkout becomes an object with four things. A name, so we can say which step we mean. An action, which does the step. A compensation, which is the action that cancels it. And an answer to one question: can this step be undone at all? For our shop, in pairs. Reserve the stock, and release it. Take the payment, and refund it. Create the order, and cancel it. Book the parcel, and cancel the booking. If this feels familiar, it is. An action and an undo on an object is the Command pattern. But one difference matters more than anything else in this video. A command's undo happens in memory, and always works. A compensation is a network call to someone else's service. It can be slow. It can be refused. It can fail. Remember that.

8. Forward, Then Backwards

And here is the orchestrator, which is the rest of it. Go forward through the steps. Run each one. After each one succeeds, add it to a list. That list is not holding anything open. Every step on it has already finished. It is simply a record of what must be undone, if a later step fails. If a step fails, stop going forward. Walk the list backwards, and run each step's compensation. One more thing, easy to miss. The orchestrator never crashes. It always returns a result describing what happened. Because a saga that can crash has no way to tell anyone what state the shop was left in. That would put us right back at the try block.

9. Who Does What

Let's put all the pieces in one place. On one side is the design we are replacing. Four calls in a try block, and a catch that writes a log line. When the courier refuses, it leaves money taken, a kettle reserved, an order confirmed, and no parcel. On the other side is the saga. A step: an action, paired with a compensation, and whether it can be undone at all. An orchestrator, which runs the steps forward keeping a list, and then backwards to undo them. And a result, with three possible values, not two. Completed. Compensated. And needs human help. Then there is the odd one out: the email service. It has no compensation at all, because there is no unsend. That is why it must go last. And one honest summary of the whole pattern. A refund is a new fact, not an erasure. An undo can be refused. And some steps have no undo at all.

10. Act One — It Usually Works

First demo: when nothing goes wrong. The boring case carries an important fact. The stock is reserved in thirty milliseconds. The payment takes a hundred, the slowest step. The order record takes twenty. The courier booking takes sixty. The email takes forty. Two hundred and fifty milliseconds, and the order is completed. Nothing clever happened. But here is the key fact. No transaction covered any of that. Each step was saved on its own. By the time the payment was taken, the stock reservation was already final. By the time the courier was called, the money had already left the customer's account for good. That is exactly why compensation is the only tool we have.

11. Act Two — Walked Backwards

Second demo: the same courier refusal, but through the saga. The first three steps succeed, just as before. Stock reserved, money taken, order created. Then the shipping step fails. The orchestrator stops going forward, and walks its list backwards. Cancel the order. Refund the payment. Release the stock. The result says: compensated. The customer owes nothing. All twenty kettles are back on the shelf. The shop is holding no money. The order says cancelled. Why backwards? It is not tidiness. Later steps depend on earlier ones. The order must be cancelled before the refund. Otherwise, for a moment, the finance team sees a confirmed order with no payment. And the stock reservation comes off last, because it made every later step possible. Reverse order is the only order in which each undo is safe. So the shop is back where it started. Approximately.

12. Three Things This Costs You

That is the whole mechanism. Most explanations of the saga pattern end here. A step with an undo, an orchestrator that walks backwards, and a happy summary. But everything so far is the easy half. There are three things that undoing costs you. One. The undo leaves a trace. It is not a rollback. Two. The undo is itself a network call to someone else's service. So the undo can fail. Three. Some steps cannot be undone at all, by anybody, ever. The rest of this video takes those three, one at a time. Do not skip them. These are the parts that will actually find you.

13. One — A Refund Is A New Fact

Cost number one. Look at the payment records after that perfectly successful compensation. They do not show nothing. They show two lines. A charge of seventy pounds ninety-five. And a refund of seventy pounds ninety-five. The total is zero. The history is not. That is not an accounting detail. A database rollback leaves no trace. It is as if the write never happened. A compensation is a new action that cancels an old one. And both stay true, forever. So the customer saw seventy pounds leave their account, and come back. They may ring up to ask why. Their bank may show it as pending for days. And the card network may keep its fee either way. Just like the holiday, where the airline charged a cancellation fee. So here is the sentence to remember. Compensation is not rollback.

14. Two — When The Undo Fails Too

Cost number two, and this one is uncomfortable. What happens if the refund fails? The payment service does not answer. The money cannot be given back. Two things happen, and both are deliberate. First, the undoing carries on anyway. The refund failed, but the order is still cancelled, and the stock is still released. A saga that gave up at the first failure would leave more broken than necessary. Second, the result says so, clearly. This is why there are three results, not two. Completed. Compensated. And needs human help. That third result names a problem no code can fix. The shop is holding seventy pounds ninety-five that it should not have. And it cannot give it back automatically. Compare that with the try block from the start. The money is in exactly the same place. The difference is that this version knows, and says so. So, in your system, where does needs human help go? A queue, a ticket, a dashboard, or a person whose job it is. If it goes nowhere, it is no better than that log line.

15. Three — There Is No Unsend

Cost number three. This demo runs the same five steps, with one change. The confirmation email is sent earlier, before the courier is booked. Then the courier refuses, just as before. Everything is undone correctly. The order is cancelled. The money is refunded. The stock goes back on the shelf. And the customer is holding an email that says their order is confirmed. It is not. No compensation can help, because there is no unsend. The only fix is a second email, apologising. Which is, once again, a new fact, not an erasure. That is why each step says whether it can be undone at all. The email step says no. So the saga records it, and reports: needs human help. Nothing in the code is broken. The order of the steps is. So here is the most practical rule in this video. Steps that cannot be undone go last, after everything that might fail. Think about your own systems. Emails, text messages, notifications, printing a label, anything a customer can see. That list is always longer than people expect.

16. Thanks for Watching

That's the Saga pattern. If you remember one sentence, make it this one. A saga undoes finished steps one by one, in reverse, but an undo is a new fact, it can fail, and some steps can never be undone, so they go last. The full source code, written notes, diagrams, and an animated walkthrough are all in the repository. It runs offline, with nothing installed except a Java development kit. Here is one exercise to try. Make a compensation fail on purpose, using a setting on the stock service. Then see which other undos still run, and what the result says. And one question to think about. Take a process you work on, and list its steps in order. Mark the ones that can never be undone. Do any of them happen before something that might fail?
