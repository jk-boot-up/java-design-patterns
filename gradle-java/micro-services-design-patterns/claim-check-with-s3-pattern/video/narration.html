1. Claim Check with S3

Hello, and welcome. This video explains the Claim Check pattern in Java, using real Amazon storage and a real Amazon queue, running on your own machine. This video is presented by Jayasekhar Konduru. First, a simple definition. When something is too big to send in a message, you put it in storage, and send a small ticket instead. Whoever receives the ticket uses it to fetch the real thing. It works like the left-luggage office at a railway station. You leave your heavy suitcase at the counter, and carry a small paper ticket. Later, the ticket gets your suitcase back. In our online store, checkout has an invoice to hand to the email service. The invoice is a big P D F file. So checkout puts the P D F in storage, and sends the email service a ticket saying where to find it. By the end, you will hear a real queue refuse an invoice. A ticket bring it back, byte for byte. Luggage that nobody collects. A delete that deletes nothing. And the bill.

2. The Scenario

Here is the scenario. Checkout makes an invoice, as a P D F file. The email service sends it to the customer. They are two separate programs, with a queue between them. A queue is a waiting line for messages. One program puts a message in, and another takes it out later. So checkout can hand the work over, and carry on. The plain Java version of this project used a queue with a size limit it made up. This time, the queue is Amazon's queue service, and the storage is Amazon's storage service. The limits are Amazon's, and so are the error messages.

3. An Invoice Too Big For The Queue

First demo: an invoice that is too big for the queue. The queue service is called S Q S, short for Simple Queue Service. The demo asks it how long a message may be. The answer is just over one million bytes. A business customer's monthly invoice is one and a half million bytes. But a message must be text. So the P D F is first written out as letters, in a format called base sixty-four. That makes two million characters. S Q S refuses it. It says the message must be shorter than its limit. That is not a rule this program made up. It is the real service saying no.

4. The Services' Words

The real services bring a few words with them. Each one is simpler than it sounds. Think of the left-luggage office again. The office is the storage service, called S three, short for Simple Storage Service. A storage room in it is called a bucket. One suitcase on the shelf is called an object. That is just a stored file. And the name on the suitcase's tag, the name you fetch it by, is called a key. The queue is S Q S, and one piece of text in it is called a message. Neither service is really on Amazon here. A program called LocalStack answers exactly as they would. It runs in a container, a small sealed box on this machine. The demo switches it on at the start, and off at the end.

5. Why A Smaller PDF Fails Too

Here is the surprise in the first demo. A P D F is raw bytes, and a message must be text. So the bytes are spelled out with letters. That spelling uses four letters for every three bytes. So the file grows by a third on the way in. The demo tests the edge. A P D F of about seven hundred and eighty-six thousand bytes becomes exactly the limit, and is accepted. One byte more, and it is refused. So a file does not fit just because it is under the limit. It only fits if it is under three quarters of the limit.

6. Send The Ticket, Not The Luggage

Second demo: send the ticket, not the luggage. Checkout puts the P D F in an S three bucket. It is stored under a random key, thirty-six characters long, that nobody could guess. Only then does checkout send a ticket. The ticket is only a hundred and thirteen bytes of text. It names the bucket, the key, the size, and a checksum. A checksum is a short fingerprint worked out from every byte of the file. If one byte changes, the fingerprint changes. The email service takes the ticket, and fetches one and a half million bytes. It checks the fingerprint, and the file is identical to what was sent. Then it deletes the stored file. And only after that, it deletes the message. Nothing is left in either service.

7. Where The Invoice Lives

Here is the whole picture, in words. There are four parts, in order. First, checkout. It stores the P D F, and then sends the ticket. Second, the S three bucket. It holds the P D F under its key, however big it is. Third, the S Q S queue. It carries only the ticket, about a hundred bytes. Fourth, the email service. It takes the ticket, fetches the P D F, checks the fingerprint, and then clears up both. The rule that holds it together is the order. Store before you send. And delete the message only after the file has been fetched and checked.

8. Luggage Nobody Collected

Third demo: luggage nobody collected. Checkout sends ten invoices by ticket. The email service collects six, and then stops. So S three still holds four invoices, and S Q S still holds four tickets for them. That is fine. They will be collected later. Then an eleventh invoice is stored. But the send that should follow it fails. The queue says it does not exist. Now storage holds five invoices, but the queue holds only four tickets. One invoice has no ticket at all. And nobody will ever ask for it. Storing and sending are two separate steps. And a program can stop between them.

9. The Same Key, Twice

Fourth demo: the same key, used twice. This bucket names each file after its order. So the invoice for order ten forty-two is stored under a key made from that order number. And its ticket is sent. Then a corrected invoice for the same order is stored under the same key. Before the first ticket has been collected. S three keeps only one file. The new file has quietly replaced the old one. The email service redeems the first ticket. The fingerprint on the ticket does not match the file it gets back. So it refuses to send it. Without that checksum, a customer would have received an invoice nobody meant to send.

10. A Delete That Deletes Nothing

S three has an answer to that, and it has a catch. A bucket can be told to keep every version of every file. This is called versioning. Storing under a key that is already used then adds a new version, and the old one stays. Each version has its own I D, and the ticket carries it. So now, the first ticket gets the first invoice, exactly. Here is the catch. The email service deletes the key, just as before. A listing of the bucket now shows no files at all. But two versions are still stored, and still paid for. The delete only added a marker, a note saying the key is deleted. This is called a delete marker. Only deleting each version by its own I D really empties the bucket.

11. How Long Each One Waits

Fifth demo: how long each one waits. Luggage nobody collects has to be cleared away eventually. S three can do that by itself. A rule removes every file a set number of days after it was stored. This is called a lifecycle rule, and its smallest unit is one whole day. So the invoice is marked to expire at a midnight, between one and two days away. The queue has its own clock. It keeps a ticket that nobody has taken for four days. The demo cannot wait a day, so it removes the invoice just as the rule would. One ticket is still waiting. A slow email service redeems it. And S three says the key does not exist. The ticket outlived its luggage.

12. The Bill

Finally, the bill. The demo counts every request the two services receive. An ordinary invoice of six hundred thousand bytes is small enough to send whole. That takes three requests: send, receive, and delete the message. And the queue carries eight hundred thousand bytes of text. The same invoice sent by ticket takes six requests. Store the file. Send the ticket. Receive it. Fetch the file. Delete the file. Delete the message. But the queue carries only a hundred and seventeen bytes. So the ticket costs twice the requests, and two services to run and pay for. And there is a gap between storing and sending.

13. What The Simulation Left Out

The plain Java version got the shape right. Store the luggage, send a ticket, redeem it, check the fingerprint, clear up, and expire what nobody collects. All of that holds on real S three and S Q S. But it left out three things. First, its limit was a number it chose, and it counted bytes. The real limit counts text. So a file that looks small enough grows by a third, and is refused. Second, its storage never let two files share a name. And third, its delete really deleted. A versioned bucket keeps every byte, and bills you for it.

14. The Verdict

So, here is the verdict. Use a claim check when a file will not fit in a message, or should not travel through one. Then settle four things, because neither service will assume them. One. Store every file under a random key, and never reuse one. Two. Put a checksum on every ticket, and check it before you trust the file. Three. Store first, then send. And have a rule that clears away what nobody claims. Four. Make the queue forget a ticket before storage forgets the file. So no ticket outlives its luggage.

15. What Is Real, And When Not

A quick, honest note about this demo. Both services are played by LocalStack, version four point fourteen, in a container the demo starts and stops by itself. That version is held back on purpose, because newer ones need a LocalStack account. The code is ordinary Amazon code, using the newest Amazon library for Java. It would run unchanged against Amazon itself. You only need Docker, or a similar container tool, switched on first. Every number you heard comes from the program's own output. So, when is this too much? If your files are small, a ticket adds steps for nothing. If the receiver needs the data at once, and storage is slow, the ticket costs more than it saves. And it always means two services to run, not one.
