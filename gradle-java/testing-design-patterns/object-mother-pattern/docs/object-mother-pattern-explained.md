# Object Mother / Test Data Builder, Explained

## The pattern in one sentence

An Object Mother hands tests named, ready-made objects; a Test Data Builder
starts from defaults and lets each test state only what it cares about.

## The 5 acts

### 1. Built by hand

A test for the shipping rules builds an order by hand: a customer with a
name, an email and a VIP flag, a country, a line with a product, a quantity
and a price, and a gift-wrap flag. Three constructors and eight values, to
check that the shipping is 4.99. Which of those eight values does the test
depend on? The reader cannot tell. And when the customer gains a new field,
every test like this must be edited.

### 2. An Object Mother

An Object Mother collects ready-made orders under names that say what they
are. `TestOrders.domestic()` ships for 4.99, `vip()` ships free and
`international()` pays 15.00. Each test is one line, and when the customer
gains a field, it is added in one place: the mother.

### 3. The mother multiplies

The trouble starts when tests need mixes. VIP or not, abroad or not, gift
wrapped or not: three yes-or-no details make eight combinations, each needing
its own method, like `vipInternationalGiftWrapped()`. One more detail and it
is sixteen.

### 4. A Test Data Builder

A Test Data Builder starts from sensible defaults for everything, and has one
method per detail. A VIP order to France is
`anOrder().vip().shippedTo("FR").build()`, and pays 15.00, because free VIP
shipping is UK only. A gift-wrapped VIP order pays 2.00. Any mix fits in one
line, and the line names exactly what the test cares about.

### 5. The bill

A free-shipping test was written as a bare `anOrder().build()`, back when the
default price was 60.00, over the free-shipping line. Someone lowered the
default to 30.00; the order now pays 4.99, and the test fails with no visible
reason. The fix is `anOrder().totalling(60).build()`: a test states everything
it relies on, and defaults stay dull.

## The verdict

Use a mother for a few well-known, named cases, and a builder when tests need
many mixes. Keep defaults dull and valid, and let each test name every value
its assertion depends on.

## How to recognise this in code you did not write

- Classes named `TestOrders`, `Fixtures` or `...Mother` in `src/test`.
- Static methods such as `anOrder()` or `aCustomer()` returning builders.
- Tests that read as a sentence: `anOrder().vip().shippedTo("FR")`.

## Where you have already met this

- Builders generated by Lombok's `@Builder`, or written by hand in `src/test`.
- Fixture factories such as Instancio or Java Faker helpers.
- Ruby's factory_bot and Python's factory_boy, the same idea in other languages.
